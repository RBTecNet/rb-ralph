# RB Ralph

RB Ralph is the optional execution consumer for RB Harness artifacts. It is a
provider-neutral Bash run manager: implementation agents change code, a
technical-manager LLM reviews evidence, and deterministic gates retain final
authority over executable validations.

> **Security default:** RB Ralph runs provider calls in YOLO mode unless
> `--protected` is supplied explicitly. YOLO grants the selected LLM CLI the
> permissions available to the current operating-system user. Run untrusted
> projects inside a disposable VM, container, or dedicated account.

RB Ralph consumes the model-neutral `rb-manifest/v1` and `rb-execution/v1`
artifacts generated by RB Harness. Those documents do not require Ralph: they
may also be delivered directly to any capable LLM CLI.
It additionally understands the optional, additive `rb-operational/v1`
contract for clean-room product acceptance.

## Installation

The runtime supports Bash 3.2 or newer, including the Bash version bundled
with macOS. It deliberately avoids Bash 4-only features such as associative
arrays. Node.js, Git, and the CLIs selected as agent or manager providers must
also be available on the machine.

### Current user, without sudo

From the cloned `rb-ralph` directory:

```bash
./rb-ralph.sh --install
```

The default prefix is `~/.local`. If necessary, add its binary directory to
your shell once:

```bash
export PATH="$HOME/.local/bin:$PATH"
```

Put that export in `~/.bashrc`, `~/.zshrc`, or the startup file used by your
shell to make it permanent. A different user-owned prefix is also supported:

```bash
./rb-ralph.sh --install --prefix "$HOME/tools"
```

`rb-ralph.sh --install` installs the complete runtime, not just one Bash file.
Re-run the same command to upgrade it. Use `--force` only if the target
`bin/rb-ralph` is a regular file that should be replaced.

### System-wide prefix

An administrator can install the same layout under `/usr/local`:

```bash
sudo ./rb-ralph.sh --install --prefix /usr/local
```

No auxiliary resource is written directly to `/bin`. The layout is:

```text
<prefix>/
├── bin/
│   ├── rb-ralph -> ../libexec/rb-ralph/bin/rb-ralph
│   └── rb-ralph-watch -> ../libexec/rb-ralph/bin/rb-ralph-watch
└── libexec/rb-ralph/
    ├── bin/{rb-ralph,rb-ralph-watch}
    ├── adapters/{adapter-utils,codex,claude,opencode}.sh
    ├── core/rb-harness.cjs
    ├── lib/{evidence,control-plane,process-supervisor,operational-verifier,provider-telemetry,usage-summary,dashboard}.cjs
    ├── VERSION
    ├── pricing.example.json
    └── README.md
```

The launcher resolves its real destination through symlinks, independently of
the current working directory. `--project .` deliberately remains relative to
the directory from which the user invoked Ralph.

To package a different compatible RB Harness CLI:

```bash
./rb-ralph.sh --install --prefix "$HOME/.local" \
  --core-cli /path/to/rb-harness
```

### Uninstallation

Use the same prefix chosen during installation:

```bash
./rb-ralph.sh --uninstall
./rb-ralph.sh --uninstall --prefix "$HOME/tools"
```

The uninstaller removes only the RB Ralph resource tree and its launcher
symlink. It refuses to delete a regular launcher file it cannot safely identify
as its own.

### Source tree and first commands

Installation is optional during development:

```bash
./rb-ralph.sh --project /path/to/project --list
./rb-ralph.sh --project /path/to/project --dry-run
```

After installation, the same commands work from any directory:

```bash
cd /tmp
rb-ralph --project /path/to/project --list
rb-ralph --project /path/to/project --plan <artifact-id> --dry-run

cd /path/to/project
rb-ralph --project . --plan <artifact-id> --provider codex
```

Run `rb-ralph --help` for a compact command tutorial and the full option list.
Confirm the exact source or installed build at any time with:

```bash
rb-ralph --ver
rb-ralph --version
# RB Ralph 0.5.2
```

The installer prints and copies the same `VERSION` marker, so a source upgrade
and the globally installed launcher can be compared without relying on file
timestamps.

## Live terminal dashboard

RB Ralph has its own terminal identity: the wide dashboard and `--help` show
the RB Ralph ASCII wordmark alongside Ralph, the project mascot — a calm
capybara watching over less-calm agents. Narrow or short terminals
automatically use the compact one-line brand so gates and evidence retain
priority over decoration.

Every interactive invocation opens with a short animated splash: the large RB
Ralph wordmark and Ralph the capybara, cycling green -> purple -> orange for
about 1.8 seconds. It is drawn on the terminal's alternate screen buffer, so it
leaves no trace in the scrollback and the run starts on a clean screen. The
splash is purely cosmetic and never changes execution state; the brand shown
inside the run itself stays static.

It is skipped automatically whenever it would be noise: non-interactive output
(pipes, redirects, CI), `--list`, `--dry-run`, `--help`, `--version`,
`TERM=dumb`, and terminals smaller than 34x16.

```bash
rb-ralph --splash                             # play it on its own and exit
rb-ralph --project . --no-splash              # skip it for this invocation
RB_RALPH_SPLASH=0 rb-ralph --project .        # disable it entirely
RB_RALPH_SPLASH_MS=800 rb-ralph --project .   # make it shorter
```

`--splash` is the explicit request, so it plays even when `RB_RALPH_SPLASH=0`
is set in the environment.

Start a run with its embedded TUI:

```bash
rb-ralph --project . --provider codex --dashboard
# --tui is an equivalent alias
```

The runner streams model output into its normal evidence logs while the
dashboard owns the terminal screen. A fixed-height `LOG RECENTE` box below the
phase table shows the latest four useful lines from the active executor,
validation, or manager log. Structured Codex JSONL events are reduced to
readable session, command, message, token, and error summaries; the complete
unaltered evidence remains in the referenced log file. The box never grows, so
verbose providers cannot push the rest of the TUI downward. Pressing `q` is
intentionally disabled for the
embedded view. When the run finishes or fails, its final frame remains open
with phases, gates, usage, and costs frozen for inspection; press `Enter` to
close it. `Ctrl-C` still interrupts an active runner and restores the terminal.

Observable state is written atomically for every execution, even without
`--dashboard`. A second terminal can therefore attach before, during, or after
a run:

```bash
rb-ralph-watch --project /path/to/project
rb-ralph --project /path/to/project --watch

# Render one snapshot in a log, CI job, or non-interactive shell
rb-ralph-watch --project /path/to/project --once --no-color
```

The panel shows run duration and status, current phase/activity/attempt,
phase/task progress, provider calls, input tokens, cache reads, cache writes,
output tokens, total tokens, and cost availability. Every phase also exposes
four live gates: `G0` executor exit, `G1` changed-code evidence, `G2`
deterministic validations, and `G3` technical-manager decision. Their states
are pending, running, passed, failed, or delegated/skipped. The dashboard
also shows the manager's recorded reason for COMPLETE, RETRY, BLOCKED, and
protocol failures. Final blockers remain visible in a dedicated reason box,
with a reference to the persisted event. The dashboard reader is isolated
from the executor and never mutates execution state.

Provider failures are normalized into actionable messages without copying
credentials into dashboard state. Known billing, authentication, executable,
provider/model, permission, and timeout failures identify the affected role and
model, point to the complete local log, and suggest the relevant recovery. For
OpenCode, Ralph distinguishes Zen (`opencode/...`) from a Go subscription
(`opencode-go/...`). Terminal billing, authentication, provider, model, and
permission errors become actionable external blockers without rerunning the
executor. Transient or malformed manager responses retry only the manager over
the already captured evidence; if that recovery is exhausted, the run enters a
resumable `PAUSED` state instead of replacing the original cause with a generic
failure.

### Token and cost accounting

Built-in Codex and Claude adapters request structured output only when Ralph
activates telemetry. Direct standalone adapter use retains the original text
mode. Each provider call writes one `rb-ralph-usage/v1` record under
`usage/<execution-id>/` in the run directory. Re-running the same plan creates
a new execution directory: the dashboard and `usage-summary.tsv` report only
the current invocation, while records from earlier invocations remain available
for audit without leaking old provider/model names into the live panel.

- Codex JSONL supplies measured input, cached-input, and output tokens.
- Claude JSON supplies its cache token classes and, when returned by Claude
  Code, the provider's `total_cost_usd`.
- A custom adapter may overwrite `RB_RALPH_TELEMETRY_FILE` with a compatible
  `rb-ralph-usage/v1` JSON record. If it does not, the call remains explicitly
  marked unmeasured.
- Native provider cost wins over every estimate. Ralph never guesses a price
  for an unknown model.

The optional custom-adapter record is a JSON object with this stable shape:

```json
{
  "schema": "rb-ralph-usage/v1",
  "provider": "provider-name",
  "model": "exact-model-id",
  "role": "agent",
  "phaseId": "P01",
  "taskId": null,
  "attempt": 1,
  "measured": true,
  "inputTokens": 0,
  "cachedInputTokens": 0,
  "cacheCreationInputTokens": 0,
  "outputTokens": 0,
  "totalTokens": 0,
  "costUsd": null,
  "costSource": "unavailable"
}
```

The runner creates an unmeasured placeholder before invoking a command. A
custom adapter should replace the target atomically when it has provider usage;
it must use `costSource: "provider"` only for a native USD value. Missing usage
never affects `COMPLETE`, retries, or validation authority.

For providers that report tokens but no cost, copy the example catalog, enter
reviewed prices per one million tokens, and select it for the run:

```bash
cp pricing.example.json "$HOME/.config/rb-ralph-pricing.json"

rb-ralph --project . --provider codex --dashboard \
  --pricing-file "$HOME/.config/rb-ralph-pricing.json"
```

The catalog format is:

```json
{
  "currency": "USD",
  "models": {
    "exact-provider-model-id": {
      "inputPerMillion": 0,
      "cachedInputPerMillion": 0,
      "cacheWritePerMillion": 0,
      "outputPerMillion": 0
    }
  }
}
```

Replace every zero with a reviewed current price. Estimates are labeled
`configured-pricing`; provider values are labeled `provider`; mixed and partly
unknown totals remain visibly identified. `RB_RALPH_PRICING_FILE` is the
environment equivalent of `--pricing-file`. Prices use USD; Ralph does not
perform an implicit currency conversion. API-list prices may not equal the
amount billed by a subscription-based CLI account, so the panel never presents
configured estimates as an invoice.

## RB Harness CLI discovery

The deterministic contract CLI is resolved in this order:

1. `--core-cli <path>`;
2. `RB_RALPH_CORE_CLI`;
3. the CLI packaged under `$RB_RALPH_HOME/core/`;
4. `rb-harness` found on `PATH`;
5. an actionable error without starting a provider.

`RB_RALPH_HOME` is the explicit resource-root override. Normal source and
installed use does not require setting it. It exists for packagers, tests, and
controlled relocations and must point to a complete resource tree. No path from
Codex caches or from the monorepo's internal layout participates in discovery.

## Current capabilities

- Discovers ready plans through `rb-manifest/v1`; it never guesses paths.
- Rejects stale hashes, invalid trees, unsupported contracts, and malformed
  phase/task documents before starting a provider.
- Selects a plan by artifact ID or manifest path.
- Enumerates and extracts phases through the shared deterministic parser.
- Skips phases whose document tasks are all checked.
- Runs an implementation agent followed by an evidence-bound technical-manager
  review, with isolated manager-call recovery when necessary.
- Uses provider-neutral executable adapters that read prompts from stdin.
- Includes built-in Codex and Claude Code adapters, including mixed-provider
  runs.
- Runs every backtick-delimited validation command in the phase and prevents
  manager approval from overriding a deterministic failure.
- Passes prior manager feedback and validation logs into retry prompts.
- Runs independent pending tasks concurrently when every selected task is
  marked parallel-safe and no selected task depends on another.
- Gives each parallel agent only its task plus phase context, reducing repeated
  prompt content and preventing sibling-task scope leakage.
- Isolates concurrent task agents in detached Git worktrees created from one
  immutable snapshot, then check and combine their patches before changing the
  primary working tree.
- Preserves pre-existing tracked and non-ignored untracked local changes in the
  execution snapshot without staging, stashing, or committing the current
  branch.
- Fails closed when sibling patches touch the same path or otherwise conflict,
  and retains the task patches as run evidence.
- Rejects prompts above a configurable byte bound before starting a provider.
- Publishes a live terminal dashboard and normalized per-call token/cost
  telemetry without making telemetry a completion gate.
- Normalizes provider usage limits, waits within configured bounds, and retries
  availability without consuming a logical implementation attempt.
- Persists append-only events, prompts, phase snapshots, and logs under
  `.rb/runs/<artifact-id>-<sha12>/`.
- Captures live provider output and optional executor submissions outside the
  project, then publishes canonical run evidence atomically. Existing
  orchestrator artifacts are integrity-checked so an executor cannot silently
  rewrite prompts, logs, events, validations, or prior evidence.
- Resumes phases already accepted by the manager for the same plan hash.
- Supports progress-aware implementation retries, strategy recovery, a hard
  per-invocation cap, and resumable circuit-breaker pauses.
- Persists a cumulative finding ledger. Every manager RETRY remains open across
  later attempts until a COMPLETE decision resolves it against the current
  changed-path and validation fingerprint; newer feedback never erases older
  findings.
- Detects built-in-provider turns that exit successfully with no workspace
  delta and no completed final-response marker. Those incomplete turns receive
  bounded executor-only retries and never spend a manager review or logical
  implementation attempt.
- Prevents manager approval from overriding a failed agent process or isolated
  patch integration.
- Adds a runtime-only final phase (`RBF`) that verifies the completed product
  through a real consumer boundary in clean-room isolation, then uses the same
  bounded executor/manager retry machinery to repair escaped integration,
  packaging, startup, configuration, or documentation defects.
- Executes an optional `rb-operational/v1` contract deterministically and still
  requires an independent manager audit. Existing projects without the
  contract use a dynamic evidence-grounded fallback.
- Optionally bootstraps bounded RB Memory context through MCP and checkpoints
  every accepted phase using the manifest's stable project ID.

## Final operational acceptance

The final audit is enabled by default:

```bash
rb-ralph --project . --provider codex
```

It appears in logs and the dashboard as `RBF — Independent operational
acceptance`. `RBF` is created only in runtime state; Ralph never adds it to or
silently changes `PHASES.md`, so the `rb-execution/v1` contract remains intact.
The phase has the normal four gates: executor correction, changed-path
evidence, deterministic operational proof, and independent manager review.

Ralph discovers `OPERATIONS.json` in this order:

1. `--operations <path>` (alias `--operational-contract`);
2. `RB_RALPH_OPERATIONAL_CONTRACT`;
3. beside the selected `PHASES.md`;
4. `.rb/OPERATIONS.json`;
5. `.rb/init/OPERATIONS.json`;
6. `.rb/context/OPERATIONS.json`.

The file uses `rb-operational/v1`. Its commands are argument arrays rather than
shell strings, and scenarios may select `linux`, `darwin`, and/or `win32`.
Ralph copies the project to a temporary directory, excludes Git/run state and
local `.env` variants, constructs a minimal environment, executes the
applicable scenarios, terminates managed processes, and removes the copy.
`cleanRoom.exclude` should additionally name the project's dependency trees,
caches, build products, and local state.

Only scenarios applicable to the current host run locally. Native coverage for
multiple claimed operating systems requires matching hosts/CI runners, an
emulator, or another real declared mechanism. Ralph never treats a Linux run as
proof that a Windows or macOS desktop window launched correctly.

The contract supports generic `command`, `process`, `http`, `tcp`, and `file`
steps. Process readiness and checks may observe stdout, HTTP, TCP, or files.
`${RB_VERIFY_ROOT}` is the isolated root and `${RB_VERIFY_PORT}` is an available
local port. This is intentionally about observable products, not one stack:

- desktop/mobile applications build or package and use real UI automation,
  accessibility/screenshot evidence, launch behavior, or another supported
  platform observation;
- CLIs execute their installed public command and inspect status/output;
- libraries compile and run a minimal external consumer;
- services use their real protocol (HTTP is only one option);
- plugins and packages install into a representative disposable host;
- jobs, workers, firmware, and data products prove their supported trigger and
  durable output.

If no contract exists, the executor and manager derive the smallest honest
scenario from README, specs, packaging metadata, tests, and actual entrypoints.
They are explicitly forbidden from treating mocks or an existing running
process as end-to-end evidence. A genuine visual/manual check is reported as
manual unless suitable automation or observable evidence exists.

Use the opt-out only deliberately, for example while debugging the runner:

```bash
rb-ralph --project . --provider codex --no-final-audit
```

`--validation-mode manager` does not disable an explicitly declared
`OPERATIONS.json`; the operational contract remains a deterministic completion
gate. A failing operational step forces `RETRY` even if the manager answers
`COMPLETE`.

The operational result has one owner: `RBF`. A normal phase may create and run
the structural `operations validate` command, but its acceptance criteria must
not require the later clean-room scenario to pass. That would make `RBF` depend
on a phase which itself depends on `RBF`.

## Provider adapter contract

Both commands are ordinary executables. From a source checkout:

```bash
bin/rb-ralph \
  --project /path/to/project \
  --plan feature-example-execution \
  --agent-cmd /path/to/agent-adapter \
  --manager-cmd /path/to/manager-adapter
```

They receive a prompt on stdin and run from the target project root. The
following environment is available:

- `RB_RALPH_ROLE`: `agent` or `manager`.
- `RB_RALPH_PROJECT_ROOT`.
- `RB_RALPH_PLAN_PATH`.
- `RB_RALPH_PHASE_ID`.
- `RB_RALPH_PHASE_TITLE` for the manager role.
- `RB_RALPH_ATTEMPT`.
- `RB_RALPH_MANAGER_RETRY` for manager calls (`1` is the initial review;
  larger values review the same evidence again).
- `RB_RALPH_AGENT_EVIDENCE_DIR` for the executor role. It is an isolated
  optional submission directory outside the project; `.rb/runs` remains
  orchestrator-owned.
- `RB_RALPH_AGENT_LOG` for the manager role; this is the canonical executor
  output published after the executor process exits.
- `RB_RALPH_VALIDATION_LOG` for the manager role.
- `RB_RALPH_CHANGED_PATHS_FILE` for the manager role.
- `RB_RALPH_AGENT_EXIT_CODE` for the manager role.
- `RB_RALPH_TELEMETRY_FILE`: per-call usage record the adapter may populate.
- `RB_RALPH_OPERATIONAL_CONTRACT`: absolute path when a deterministic
  operational contract was selected, otherwise empty.

`RB_RALPH_PROJECT_ROOT` is the primary project root in shared mode and the
agent's detached task worktree in isolated mode. `RB_RALPH_TASK_ID` is set only
for a task-scoped parallel agent.

A custom manager adapter must provide its model with read access to
`RB_RALPH_PROJECT_ROOT` and the evidence paths above. The manager prompt
contains a bounded changed-path summary, but intentionally does not duplicate
arbitrary source and log contents. An adapter for a remote model without
filesystem access must therefore implement its own bounded and redacted
evidence transport before it can satisfy this contract; otherwise it must
reject manager use clearly.

The agent may implement the phase. The manager must inspect without repairing
and return:

```text
RB_RALPH_DECISION: COMPLETE
RB_RALPH_REASON: Every criterion is covered and focused validations pass.
```

`RETRY` and `BLOCKED` are the other valid decisions. Adapters own CLI-specific
arguments, models, permissions, authentication, and output normalization, so
the run manager does not hard-code Codex, Claude, or another provider.

Built-in-provider executors are also asked to end a genuinely completed final
response with `RB_RALPH_EXECUTOR_STATUS: COMPLETE`. Ralph consults this marker
only when the provider exited zero and produced no workspace delta; absence is
then treated as an incomplete provider turn rather than paid manager evidence.
Custom adapters remain responsible for their own completion semantics.

Ralph does not add secret-like files such as `.env`, private keys, or
credential files to its changed-path summary. Custom adapters must avoid adding
secrets to prompts or logs and apply equivalent redaction to any evidence they
transport.

## Built-in providers

The executor is the primary configuration. The manager inherits it unless a
manager option is given explicitly:

| Command options | Executor | Manager |
| --- | --- | --- |
| `--provider codex` | Codex | Codex |
| `--agent-provider codex` | Codex | Codex, inherited |
| `--agent-provider claude --manager-provider codex` | Claude | Codex, explicit |
| `--agent-provider opencode --manager-provider claude` | OpenCode | Claude, explicit |
| `--agent-cmd /path/agent` | `/path/agent` | `/path/agent`, inherited |
| `--agent-cmd /path/agent --manager-cmd /path/manager` | `/path/agent` | `/path/manager`, explicit |

Role-specific options override `--provider` regardless of argument order.
Provider and command cannot both be specified explicitly for the same role. A
manager-only configuration is rejected because the executor is the required
primary role.

“Same agent” means the same adapter/provider and, by default, the same model.
It does not mean the same conversation: executor and manager are separate,
ephemeral invocations with no shared session. An explicit manager model still
takes precedence over inherited model configuration.

### Model selection by role

Model selection is provider-neutral at the runner boundary:

```bash
# Same model for both calls
rb-ralph --project . --provider claude --model sonnet

# Claude Opus implements; Claude Sonnet reviews
rb-ralph --project . --provider claude \
  --agent-model opus \
  --manager-model sonnet

# OpenCode resolves each provider/model identifier
rb-ralph --project . --provider opencode \
  --agent-model deepseek/deepseek-chat \
  --manager-model openrouter/minimax/minimax-m2.1

# Providers and models may both differ
rb-ralph --project . \
  --agent-provider opencode \
  --agent-model openrouter/moonshotai/kimi-k2.5 \
  --manager-provider claude \
  --manager-model opus
```

`--agent-model` and `--manager-model` override `--model` regardless of argument
order. If only `--agent-model` is supplied and the manager uses the same
inherited adapter, the manager inherits that model. An explicitly different
provider does not inherit a provider-specific model ID; select its model with
`--manager-model`.

The environment equivalents are `RB_RALPH_MODEL`, `RB_RALPH_AGENT_MODEL`, and
`RB_RALPH_MANAGER_MODEL`. Existing provider-specific model variables remain
compatible. Custom adapters receive the effective model for the current call in
`RB_RALPH_MODEL`, plus both resolved role values in `RB_RALPH_AGENT_MODEL` and
`RB_RALPH_MANAGER_MODEL`.

Use Codex for both roles from a source checkout:

```bash
bin/rb-ralph \
  --project /path/to/project \
  --plan feature-example-execution \
  --provider codex
```

Enable up to four independent task agents:

```bash
bin/rb-ralph \
  --project /path/to/project \
  --plan feature-example-execution \
  --provider codex \
  --parallel 4 \
  --isolation worktree
```

Parallelism is conservative. If any pending task has `Parallel safe: false` or
depends on another pending task in the phase, RB Ralph automatically uses one
sequential phase agent. Parallel execution requires `--isolation worktree`; a
shared working tree is rejected before an implementation provider starts.
Worktree isolation requires a Git repository with an initial commit.

The isolated snapshot includes committed files, tracked local changes, and
non-ignored untracked files. Git-ignored dependencies and build outputs are not
copied into detached worktrees. Each task produces a binary patch; RB Ralph
applies the patches first to a separate integration worktree and only applies
the combined patch to the primary tree when all checks succeed. Changes under
`.rb/` are rejected because documentation and run evidence belong to the run
manager. Patches that touch the same path are rejected even when their hunks
would merge cleanly. Any overlap or conflict leaves the primary tree unchanged
and stores individual patches under the active run's `patches/` directory.

Use Claude Code for both roles:

```bash
bin/rb-ralph \
  --project /path/to/project \
  --plan feature-example-execution \
  --provider claude
```

Or mix providers:

```bash
bin/rb-ralph \
  --project /path/to/project \
  --plan feature-example-execution \
  --agent-provider claude \
  --manager-provider codex
```

Use OpenCode with any configured `provider/model` ID:

```bash
opencode models --refresh
opencode models

rb-ralph --project . --provider opencode \
  --agent-model deepseek/deepseek-chat \
  --manager-model anthropic/claude-opus-4-1
```

The OpenCode adapter uses `opencode run --dir <project> --model <id>`. Model IDs
are intentionally passed through without a hard-coded catalog, so new DeepSeek,
MiniMax, Kimi, Anthropic, OpenAI, or local models become available as soon as
the installed OpenCode provider exposes them.

## Permission policy: YOLO by default

Without a permission option, both executor and manager use YOLO mode:

```bash
rb-ralph --project . --provider codex
# equivalent explicit form
rb-ralph --project . --provider codex --yolo
```

For built-in Codex calls, YOLO passes
`--dangerously-bypass-approvals-and-sandbox`. For built-in Claude calls, it
passes `--permission-mode bypassPermissions` and
`--dangerously-skip-permissions`. OpenCode receives `--auto` and an inline
`permission: "allow"` override. This applies independently to executor and
manager calls, including inherited or mixed providers.

Protected execution must be requested explicitly:

```bash
rb-ralph --project . --provider codex --protected
rb-ralph --project . --agent-provider claude --manager-provider codex --protected
```

In protected mode, Codex uses `workspace-write` for the implementation agent
and `read-only` for the manager. Configure models with
`RB_RALPH_CODEX_AGENT_MODEL`, `RB_RALPH_CODEX_MANAGER_MODEL`, or the shared
`RB_RALPH_CODEX_MODEL`. When only the agent model is set and the manager is
inherited, Ralph uses that model for both roles. Setting the manager model keeps
an explicit override.

In protected mode, Claude uses `acceptEdits` for the implementation agent and
`plan` for the manager. Configure models with
`RB_RALPH_CLAUDE_AGENT_MODEL`, `RB_RALPH_CLAUDE_MANAGER_MODEL`, or the shared
`RB_RALPH_CLAUDE_MODEL`. Optional bounds are
`RB_RALPH_CLAUDE_MAX_TURNS` and `RB_RALPH_CLAUDE_MAX_BUDGET_USD`.
Claude model inheritance follows the same rule.

`RB_RALPH_PERMISSION_MODE=protected` is the environment equivalent. Existing
provider-specific variables such as `RB_RALPH_CODEX_AGENT_SANDBOX` and
`RB_RALPH_CLAUDE_MANAGER_PERMISSION_MODE` remain explicit lower-level
overrides.

OpenCode, MiniMax, DeepSeek, and other CLIs connected through `--agent-cmd` or
`--manager-cmd` receive `RB_RALPH_PERMISSION_MODE=yolo|protected` and
`RB_RALPH_YOLO=1|0`. Their adapter must translate those values to the provider's
native CLI flags. A custom adapter that cannot enforce `protected` must exit
with a clear error instead of silently running unrestricted.

Authentication remains the responsibility of each installed CLI. The TUI
always identifies new runs as `ACESSO YOLO` or `ACESSO PROTEGIDO`.

## Context and continuity bounds

Every provider invocation is a fresh, non-persistent call. Continuity comes
from versioned artifacts and run evidence, not a provider chat session:

- sequential agents receive only the validated current phase;
- parallel agents receive only their task plus phase metadata;
- retries receive the previous manager reason and paths to prior executor,
  validation, and changed-path evidence;
- managers receive the validated phase, executor exit status, changed source
  paths, executor output, validation commands, each validation's output and
  exit status, and pending manual validations;
- completed phases resume only when the selected plan SHA-256 is unchanged.

Changed files are summarized by path and inspected by the manager in the
workspace. A nonzero executor exit, failed isolated-patch integration,
or failed deterministic validation always converts an optimistic `COMPLETE`
into `RETRY`. The manager reviews and decides; it does not implement repairs.

## Bounded recovery and circuit breakers

Implementation errors do not terminate a phase merely because the old third
attempt was reached. The manager must classify code defects, failed tests,
incomplete criteria, and incorrect technical approaches as `RETRY` and provide
concrete feedback to the next fresh executor call. Ralph then evaluates whether
the attempt produced observable progress.

The default recovery budget is deliberately finite:

- `--max-attempts 3` is the consecutive no-progress window. It is no longer a
  hard total-attempt limit.
- `--max-strategy-resets 1` allows one explicit prompt escalation that tells the
  executor to discard the stalled approach and re-inspect its assumptions.
- `--max-total-attempts 12` is the absolute executor-call cap for one phase in
  one invocation, even while code keeps changing.
- `--manager-retries 3` permits three additional manager calls over the same
  executor, validation, and changed-path evidence. The executor is not called
  again for a manager transport or response-protocol failure.
- `--manager-retry-wait 5` controls the delay between those review calls.
- `--agent-idle-timeout 300` terminates the complete executor adapter process
  tree after five minutes without observable activity; on Linux this includes
  stdout/stderr plus descendant CPU and I/O progress, while other platforms use
  provider output. `--agent-timeout 3600` remains the one-hour wall-clock
  ceiling even when a process stays busy.
- `--manager-idle-timeout 180` and `--manager-timeout 900` independently bound
  each technical-manager call. A manager timeout consumes only the manager
  retry budget and never repeats the executor.

Ralph treats a changed repository path plus a non-repeated manager reason as a
progress signal. No changed path, or repeated feedback despite changes,
increments the stall counter. This is intentionally a conservative operational
heuristic rather than a claim that the change is correct; the manager and
deterministic gates retain correctness authority, while the absolute cap stops
meaningless churn.

Provider calls run under a process-group supervisor. A timeout first records a
structured `RB_RALPH_PROCESS_STATUS: TIMEOUT` block in the role's normal log,
then sends `SIGTERM` to the adapter and all descendants and escalates to
`SIGKILL` after a short grace period. This prevents orphaned model CLIs, shell
tools, development servers, or cleanup commands from holding G0/G3 forever.
On Linux, a provider that is making CPU or I/O progress but has emitted no text
for 15 seconds receives a lightweight activity heartbeat in the log and does
not trigger a false output-idle timeout. When the adapter exits normally, Ralph
also terminates descendants left in its private process group and any
reparented descendants it observed, avoiding leaked Vite/esbuild-style helpers.

An executor timeout is forwarded to the manager with its kind, configured
limit, elapsed time, partial output, changed-path evidence, and validations.
The manager is instructed to return `RETRY` with a concrete recovery approach;
Ralph also converts `COMPLETE` or `BLOCKED` back to `RETRY` for that recoverable
condition. The next ephemeral executor receives the manager strategy and paths
to the partial evidence. Normal no-progress and absolute budgets still apply,
so repeated timeouts cannot create an infinite token or process loop.

When either circuit breaker opens, Ralph records `PAUSED`, preserves every log,
prompt, validation, evidence file, and the last `RETRY` reason, and exits with
status 2. Running the same command again resumes at the next durable attempt
number and injects that persisted manager feedback into the executor prompt.
Already accepted phases remain skipped. With `--dashboard`, the final paused
frame stays visible until `Enter`.

For example, a longer but still bounded overnight run can use:

```bash
rb-ralph --project . \
  --agent-provider codex --agent-model gpt-5.6-luna \
  --manager-provider opencode --manager-model deepseek/deepseek-chat \
  --max-attempts 3 \
  --max-strategy-resets 1 \
  --max-total-attempts 12 \
  --manager-retries 3 \
  --dashboard
```

`--max-total-attempts 0` disables only the executor hard cap. It is not
recommended for unattended execution; no-progress, strategy, manager, prompt,
validation-timeout, and provider-wait guards remain active, but the explicit
hard cap is the final defense against superficial code churn.

Each role timeout accepts `0` to disable that individual guard, although doing
so is discouraged for unattended runs. Environment equivalents are
`RB_RALPH_AGENT_TIMEOUT`, `RB_RALPH_AGENT_IDLE_TIMEOUT`,
`RB_RALPH_MANAGER_TIMEOUT`, and `RB_RALPH_MANAGER_IDLE_TIMEOUT`.

The default maximum generated prompt size is 262144 bytes. Override it with
`--max-prompt-bytes N`; `0` disables this guard. This is a deterministic input
size guard and remains separate from the provider accounting in the dashboard.
The Claude adapter additionally
supports `RB_RALPH_CLAUDE_MAX_TURNS` and
`RB_RALPH_CLAUDE_MAX_BUDGET_USD`. See
[RB Harness context and continuity documentation](https://github.com/RBTecNet/rb-harness/blob/main/docs/context-and-continuity.md) for the
full policy and current boundary.

## Provider availability and continuous execution

The bundled adapters convert recognizable provider rate/usage-limit failures
to the `rb-provider-adapter/v1` availability response. RB Ralph waits and
repeats the same logical attempt:

```bash
bin/rb-ralph --project . --provider codex \
  --rate-limit-wait 60 \
  --max-limit-waits 20 \
  --max-limit-wait 3600
```

The provider may request a retry delay; `--max-limit-wait` caps any single
request. `--max-limit-waits` prevents an endless unavailable-provider loop.
Every wait is appended to `events.tsv`. Authentication failures, malformed
output, and ordinary CLI errors are not treated as rate limits. A manager
transport/protocol problem uses the separate same-evidence manager recovery
budget described above.

## Optional RB Memory continuity

Build and deploy RB Memory, create the person/team tenant in `/admin`, and give
Ralph that tenant's one-time token plus the Streamable HTTP MCP URL:

```bash
export RB_MEMORY_TOKEN="rbm_the-tenant-token"

bin/rb-ralph \
  --project . \
  --plan <artifact-id> \
  --provider codex \
  --memory-url https://memory.example.com/mcp
```

When a URL is present, memory defaults to `required`: Ralph stops if it cannot
load the bounded context or persist a completed-phase checkpoint. Use
`--memory-mode best-effort` when implementation should continue during a
memory outage, or `--memory-mode off` to disable it explicitly.

Ralph invokes the RB Memory CLI as an MCP client, derives the namespace from
`.rb/rb-manifest.json` `project.id`, stores the bootstrap response under the
active run, and labels it advisory in implementation prompts. The validated
plan and current repository always outrank memory. Accepted-phase checkpoints
include the run identity, manager reason, and validation-log reference.

Relevant options are `--memory-token-env`, `--memory-cli`, and their
`RB_RALPH_MEMORY_*` environment equivalents. See
[the RB Memory repository](https://github.com/RBTecNet/rb-ia-memory) for deployment and
client configuration.

## Deterministic validation

Default mode executes each validation command from `PHASES.md` after the
implementation agent and captures output plus exit code. Each command has a
900-second timeout when GNU `timeout` is available:

```bash
bin/rb-ralph --project . --provider codex \
  --validation-timeout 600
```

Set `--validation-timeout 0` to disable the timeout. For a controlled adapter
that owns all validation, use `--validation-mode manager`. This is less strict
and is mainly useful for non-shell validation environments.

`manual:` is reserved for a precise inspection the technical manager can make
from repository or produced evidence. `human:` means the evidence needs a
person, external device, credentialed environment, or subjective decision;
Ralph pauses during preflight instead of wasting executor/manager retries on an
observation neither role can perform.

Validation commands are reviewed project input and execute with the invoking
user's operating-system authority. They must be non-interactive and must not
perform destructive project or external-state changes.

## Safe inspection

List plans:

```bash
bin/rb-ralph --project /path/to/project --list
```

Validate the selected schedule without creating run state or invoking a model:

```bash
bin/rb-ralph \
  --project /path/to/project \
  --plan feature-example-execution \
  --dry-run
```

Both inspection commands validate `rb-manifest/v1` artifacts but do not create
`.rb/runs`.

Run the portable runner contract suite from the workspace root:

It covers real and symlink launchers, temporary installation, spaces in paths,

## Deliberate first-version limits

- Phases execute sequentially; only independent tasks inside the current phase
  may run concurrently.
- For one sequential, provider-neutral phase call, the dashboard can show the
  task list and phase activity but cannot infer exact per-task transitions; the
  pending tasks share the phase's live status. Parallel call boundaries are
  observable individually.
- Worktree isolation currently applies to parallel task agents; a sequential
  phase agent works in the primary tree.
- Built-in providers have normalized token accounting, but custom adapters may
  remain explicitly unmeasured and semantic context compaction is not yet
  implemented.
- Configured cost estimation is linear per token class. It does not model
  context-length tiers, service tiers, tool-call fees, taxes, subscription
  allowances, or currency conversion; provider-reported cost remains preferred.
- Provider limits are resumable within one running process; durable restart at
  a future wall-clock time is not yet a scheduler service.
- Progress detection is based on changed paths and manager-reason repetition;
  it does not semantically compare implementations. The hard cap remains the
  final guard against different-looking changes that do not converge.
- RB Memory integration is optional; automated semantic consolidation and
  multi-user memory governance remain future layers.
- RB Ralph never changes the current branch, creates a user-visible commit, or
  pushes. Worktree mode creates temporary detached snapshot objects internally.

Repository artifacts and append-only run evidence remain the portable source
of continuity while advanced scheduling and memory evolve independently.
